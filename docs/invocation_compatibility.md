# Agent Engine invocation compatibility

Phase 1 gate. Generated by `backend/scripts/invocation_probe.py`, run against the
live project on 2026-08-09.

- Project: `steptoe-surplus-lines-499008`
- Region: `us-central1`

Two engines were probed: `Survey  Agent v1 dev` (`4370486702397980672`, zero
production sessions, no tool use for the probe prompt) and `Steptoe Chat Agent V1`
(`8804280535544233984`, multi-agent with a retrieval tool).

## Result

| # | Endpoint | classMethod | dev agent | chat agent | Verdict |
|---|----------|-------------|-----------|------------|---------|
| A | `:query` | `query` | 404 | 404 | **FAIL** |
| B | `:query` | `stream_query` | 404 | 404 | **FAIL** |
| C | `:streamQuery` | `stream_query` | 200, 2 events | 200, 5 events, 1 call + 1 response | **PASS** |

## The assumption that was wrong

The plan proposed `:query` with `classMethod=stream_query` as the batch interface,
on the reasoning that `:query` accepts a `classMethod`. **It does not work.** Both
`:query` variants return HTTP 404 with:

```
Agent Engine Error: User-specified method `query` not found.
Agent Engine Error: User-specified method `stream_query` not found.
```

The rule the errors reveal: **`:query` dispatches only non-streaming class methods,
`:streamQuery` dispatches only streaming ones.** An ADK `AdkApp` registers
`stream_query` / `async_stream_query` / `streaming_agent_run_with_events` as
streaming methods and exposes no plain `query`, so `:query` is unusable against
these agents entirely. The `classMethod` parameter selects *within* an endpoint's
method class; it does not cross between them.

A malformed `classMethod` fails the same way — HTTP 404, not 400 — so a typo is
indistinguishable from an unsupported method by status code alone. Error handling
must read the `Error Details` body.

## Decision

**Use `:streamQuery` with `classMethod=stream_query`**, consumed to completion.

```
POST https://us-central1-aiplatform.googleapis.com/v1/
     projects/{project}/locations/{region}/reasoningEngines/{id}:streamQuery
Authorization: Bearer <ADC token>
x-goog-user-project: {project}

{"classMethod": "stream_query",
 "input": {"user_id": "...", "session_id": "...", "message": "..."}}
```

`AgentEngineInvoker` keeps this behind a single constant so a future switch is a
one-line change.

## What variant C returns

The response is a **JSON array of ADK events**, not an object. Each element carries:

```
actions, author, content, finish_reason, id, invocation_id,
long_running_tool_ids, model_version, timestamp, usage_metadata
```

Answer text lives at `$[-1].content.parts[].text` — the **last** element, not the
first. On the chat agent the answer was at `$[3]`, with earlier elements holding the
tool call and the intermediate `research_agent` output.

Two things worth noting for later phases:

- `usage_metadata` is present per event, so **token counts come free** with the
  invocation. No separate accounting call is needed (Phase 3f).
- `invocation_id` is present in the stream payload itself, so a trajectory can be
  grouped without a second `sessions.events.list` round-trip — though the events
  API remains the authority, since it is what persists.

## Trajectory completeness

The gate condition was that `sessions.events.list` must contain **both**
`functionCall` and `functionResponse`, not just the final answer.

On the chat agent, variant C persisted 5 events for one turn:

| author | parts |
|---|---|
| `user` | text |
| `research_agent` | `functionCall: search_documents` |
| `research_agent` | `functionResponse: search_documents` |
| `research_agent` | text |
| `formatter_agent` | text |

Complete trajectory: **yes**. Authors `['user', 'research_agent', 'formatter_agent']`
confirm the multi-agent pipeline is visible externally, which is what makes
span-level scoring possible without instrumenting the agent.

The dev agent produced 2 events and no tool calls — expected, since the probe prompt
("reply ok") needs no retrieval. That is a property of the prompt, not of the
interface.

## Latency

- dev agent, trivial prompt: **6.3 s**
- chat agent, retrieval + two sub-agents: **38.3 s**

A 38-second single invocation means the current `evaluation_timeout_seconds` default
of 120 s allows roughly three retrieval turns before timing out, and that batch
evaluation must be concurrent — a 50-sample serial run would take over half an hour.

## Reproducing

```bash
python backend/scripts/invocation_probe.py \
    --engine 8804280535544233984 \
    --project steptoe-surplus-lines-499008 \
    --prompt "What are the surplus lines premium tax filing requirements for Illinois?"
```

Probe sessions are created under user `agentops-probe` and deleted afterwards.
